# YA-01.1 Phase A: Serbian factual extraction

Commit scope: `feat(extraction): improve Serbian terminology and factual coverage`.
The existing Pydantic models in `assistant-api/app/schemas.py` remain the source
of truth. SQLite schema, extraction response models, audio/transcript lifecycle,
Whisper/Ollama model selection and review/dashboard templates are unchanged.
No containers were deployed or restarted. The inspection card redesign is deferred.

## Terminology resource

`assistant-api/app/terminology/sr_beekeeping.json` incrementally extends the
user-created resource. This finalization retains its uncommitted version **2**;
the content digest changes with vocabulary and interpretation. Valid authored
phrases are retained, redundant label/synonym duplicates removed, and ambiguous
mappings reclassified. Mappings use existing `InspectionData` fields and enums;
they do not create fields or translate stored JSON keys. This is an evolving
resource, not a completed linguistic encyclopedia.

The initial inventory found 14 meaningful supported entries, 18 placeholders
(including free-form `note`), one unsupported concept and two schema fields absent
from the dictionary (`trend_flight`, `trend_weight`). Seventeen placeholders now
have vocabulary, and the two trend fields have explicit contextual synonyms.
All 33 structured inspection fields have definitions; `note` intentionally remains
`{}` because it is free text rather than a separate observation to classify.

| Area | Fields with terminology |
| --- | --- |
| Colony/inspection | `inspection_type`, `bee_streets`, `bee_covered_frames`, `beekeeper_strength`, `weight_class`, `days_since_last_inspection`, `temperature_c` |
| Brood/reproduction | `brood_frames`, `open_brood`, `capped_brood`, `brood_pattern`, `queen_seen`, `eggs_seen`, `queen_cells` |
| Food/resources | `honey_frames`, `pollen_frames`, `honey_bands`, `reserves_estimate`, `pollen_intake` |
| Behavior/activity | `behavior`, `flight_activity`, `dead_bees_front`, `free_space`, `swarm_signs`, `trend_flight`, `trend_weight` |
| Health/management | `varroa_level`, `deformed_bees`, `diarrhea`, `humidity_issue`, `super_added`, `foundation_added`, `actions_taken` |

- `canonical`, when supplied, must equal the entry's supported Pydantic field.
- `serbian` and `synonyms` name the observation. They alone do not assert presence.
- `values` maps **existing enum values** to trusted spoken equivalents. For
  example, `behavior.nervozne` includes `ljute`; there is no `ljute` enum value.
- `positive`, `negative` and `unknown` contain examples of explicitly present,
  explicitly absent and unestablished observations. The full clause determines
  polarity. `Nema larvi` means `open_brood=0`; `larve nisam proveravao` means null.
  `Maticu nisam video` means `queen_seen=0`; `maticu nisam tražio` means null.
- `uncertain` retains ambiguous ordinary speech, such as `ima zasejenog` and
  `nije los venac`, or a description whose schema value is unestablished (such as
  descriptive pollen intake without a numeric rating). It is not a trusted enum
  synonym. A separate explicit observation can still establish the field.
- `note_required` retains source wording that adds meaning beyond a supported
  value: `ljute`/`agresivne` may use the closest `nervozne` category, while the
  original observation must also survive in `inspection.note`. Merely nervous
  behavior has no added aggression meaning. No new enum or health assessment is
  introduced.
- `asr_variants.contextual` labels spelling/ASR clues such as `matice vidjena` and
  `temperament mirana`. Only explicit, unambiguous context may resolve them.
  `asr_variants.uncertain` labels unreliably decoded text, including
  `zatvrno glijedla`; it stays in `inspection.note` with the affected fact null.
- Unsupported concepts require `supported: false` and a `reason`, with no mappings.
  `bee_brood_cover` describes coverage of brood by bees, which is not equivalent
  to `bee_covered_frames` (a frame count). Preserve it in notes, without a new field.
- Empty `{}` entries are valid placeholders and emit no prompt hints.

Honey band mappings separate all four schema categories:

| Observation | Existing `honey_bands` value |
| --- | --- |
| `nema venca` | `nema` |
| `tanak venac`, `slab venac` | `slabi` |
| `dobar venac`, `dobar luk` | `dobri` |
| `jak venac`, `veliki venac` | `jaki` |
| `srednji venac`, `srednji luk`, `los venac`, `nije los venac`, `venac je prisutan` | null; preserve source wording in note |

A medium band does not establish a good band, and a bad band does not necessarily
mean a thin/weak one. Large/strong descriptions apply only in honey-band context.
No reserve estimate is inferred from a band or frame count.

Queen sighting, failure to see the queen, not searching, and uncertainty are
separate observations. Eggs/larvae and the isolated noun `matica` never establish
`queen_seen=1`. A Varroa mention or a completed treatment supplies no infestation
level. Deformed bees, diarrhea and humidity record only their exact observed
symptoms; they establish no disease diagnosis. Bare queen cells without a stated
stage, pitting in brood, mold on a frame and other ambiguous descriptions remain
in notes when the existing field does not safely represent them.

Numeric flight activity (0–5) and pollen intake (0–3) need explicitly stated
ratings. Both `slab unos polena` and `nema unosa polena` remain distinct source
excerpts with null ratings; absence is not an invented scale value. Completed
foundation additions need an explicit count; otherwise retain the performed
action and its wording, with `foundation_added=null`. Plans remain in notes.
`Detaljan pregled` alone does not establish a complete inspection; explicit
`potpuni`/`kompletan pregled` does. Unsupported or incomplete concepts are retained
without extending the schema.

The loader in `app/terminology/__init__.py` rejects unknown supported fields,
mismatched canonical names, invalid enum keys, conflicting normalized enum
synonyms, conflicting positive/negative/unknown policies, conflicting ASR policies,
malformed phrase lists and duplicate JSON keys. A phrase cannot be both
unknown/uncertain/an ASR variant and an exact trusted synonym. It validates against the
Pydantic schema, without importing or opening SQLite. Dictionary loads are cached
per process; edits take effect in a new process. Tests can clear the loader cache.

Matching normalizes a separate copy to Latin, lowercase, unaccented words, with
word boundaries. The original transcript is passed to the LLM unchanged. Only
matching phrases are appended to the system prompt; unrelated entries and
placeholders are omitted. Matching cannot span sentence/clause punctuation.
At each occurrence a longer phrase suppresses shorter enclosed hints:
`nije los venac` emits uncertainty without a nested weak-band mapping, and
`nisam siguran da ima larvi` emits unknown without its inner positive hint.
Separate occurrences still survive, so `Ima larvi. Nema larvi.` supplies both
phrases for the model to resolve. `note_required` may accompany a value. Redundant
labels are omitted when the same span has a more specific policy.
A bare enum word such as `nema` never selects a honey band hint by itself.
`normalize_value()` resolves exact trusted enum synonyms for
dictionary consumers and tests; the application still strictly validates model
output and does not silently repair invalid enums.

These rules select vocabulary; they do not parse arbitrary Serbian clauses or
prove polarity, completion or correction. Unlisted negations and conditionals
still require interpretation of the original transcript. There is no global text
replacement and no deterministic rewriting of extracted facts.

## Prompt and extraction

`app/prompts/hive_semantics_v2_1.txt` is the application default. The previous v2
file remains intact and can be selected by the evaluator or by the optional
`prompt_version` keyword to `services.ollama_extract()`. Both use the same model,
JSON schema, temperature 0, seed 42, request handling and strict response parser.
The application's existing single-argument calls continue to work.

The new prompt requests all explicit schema facts, separates negation from
unchecked/uncertain observations, scopes each fact to its clause and preserves
unrepresented observations as source excerpts in notes. It distinguishes explicit
corrections from unresolved contradictions and performed actions from plans.
It prohibits inferred strength/reserves, invented activity ratings, health
assessments, scores, predictions and recommendations. Seeing larvae or the queen
does not establish eggs. Ambiguous sowing/ASR phrases do not establish eggs or
capped brood. Transcript instructions are treated as untrusted data.

Existing per-attempt metadata additionally records dictionary version and SHA-256
of its canonical JSON representation, plus system prompt character count. Ollama's
returned model, token counts and nanosecond timings remain recorded when supplied.
The hash covers dictionary content, not whitespace/formatting of its file.
No persistence or API response contract changed.

## Final integrity corrections (2026-10-29)

The hive recognizer previously accepted only the noun forms `košnica` and `društvo`.
It missed the accusative `košnicu` in the live transcript. The response parser also
left an LLM ID untouched when deterministic recognition returned no IDs, allowing
an unsupported guess to become the persisted identity.

`normalization.py` now recognizes singular case forms of both nouns, inflected
ordinals, digits, spoken numbers and common H-number spellings in Latin/Cyrillic.
Shared-noun lists, alternatives and overlapping references retain multiple IDs.
Cardinal counts before a noun are not labels. Adjacent measurement units, dates,
decimals, times, incomplete compound numbers and numeric scales followed by a new
sentence do not establish hive identity.

`services.parse_payload()` applies the same identity rules for both prompt versions:

| Transcript evidence | Result |
| --- | --- |
| One ID, model agrees or supplies null/UNKNOWN | Use the transcript ID |
| One ID, model supplies a different ID | Fail with `hive_id_conflict`; write no hive/inspection |
| Multiple IDs | UNKNOWN, requiring review |
| No recognized ID, including a model guess | UNKNOWN, requiring review |

The existing `metadata_json` stores `hive_identity` with `status` (`verified`,
`conflict`, `multiple`, `unverified` or `missing`), `transcript_ids`,
`model_hive_id`, `resolved_hive_id` and `review_required`. A failed conflict has no
resolved ID. The original model response and transcript remain unchanged, and a
later valid retry retains the failed attempt. Every persisted inspection still
starts unreviewed; verified numbering does not imply human confirmation.

For `absent_flags`, inspection of the dynamically selected hints found only its
five explicit negative observations. Neither brood nor queen hints were selected,
so overlapping dynamic synonyms do not explain the extra zeros in this case.
The static prompt contains absence examples, and broad absence instructions can
encourage copying their zeros to unrelated fields; their causal contribution has
not been measured. Schema validation accepts 0 but cannot establish source evidence.
The corrected v2.1 prompt requires evidence separately for every field, explicitly
keeps unrelated fields null and contrasts partial negatives with independent
positive observations. No keyword-based payload correction or null-to-zero filling
was added. Regression cases exercise both positives and unchecked observations
alongside unrelated negative clauses. Replayed unsupported zeros are reported as
`unsupported_extractions` and cause evaluator exit code 1.

`log2_live_asr` preserves the exact Log #2 Whisper transcript. Its expected facts
are H3, temperature 23, calm behavior, three brood frames, four honey frames and
open brood. `zatvoranog legla`, `zasijanog` and `makica vidjena` have explicit
uncertainty hints and required note excerpts; capped brood, eggs and queen sighting
remain null in the reference expectation. In particular, the unclear positive queen
phrase is not a negative observation. Separate clear observations can still
establish these fields. The evaluator flags unsupported positive or negative values;
the parser does not rewrite model observations based on these phrases.

These changes cannot guarantee live semantic accuracy. Unsupported but schema-valid
zeros can still pass application validation and be persisted as unreviewed facts.
The evaluator detects them only when reference expectations are supplied. ASR can
also produce a plausible but incorrect explicit hive number, and the finite number
grammar cannot resolve every construction. Source review remains necessary.

## Extending the dictionary

1. Check the field and enum in `schemas.py`. Reuse them exactly. For a concept with
   no genuine equivalent, document it as unsupported and keep the observation in
   notes. An unsupported marker never makes a field extractable.
2. Add ordinary expressions under `synonyms` or an existing enum under `values`.
   Put unchecked, ambiguous and ASR expressions in their corresponding lists.
   Do not treat an isolated matching word as an observation or erase negation.
3. Preserve valid expressions. For example, add `ramova s medom` to
   `honey_frames.synonyms`, not to an enum or an unrelated field. Put unresolved
   ASR strings under `asr_variants.uncertain`; a contextual variant needs a known
   reading supported by an explicit surrounding observation. Do not add speculative
   Whisper errors to trusted synonyms. Missing accents and Cyrillic transliteration
   are already handled; duplicate spellings are unnecessary.
4. Add selection and exact-normalization regressions in
   `tests/test_terminology_coverage.py`. Add positive, absent and unchecked fixtures
   when they introduce a meaningful new extraction case, including a case
   that could otherwise cause an unsupported extraction. Require source excerpts
   with `note_contains` when ambiguous or unsupported observations must survive.
5. Increment the dictionary version after released vocabulary/interpretation changes.
   Retain the existing prompt version for corrections within the same extraction
   contract; introduce another only for a material contract change. Validate, run
   the deterministic suite and compare live results when explicitly requested.
   A successful mocked response does not demonstrate model accuracy.

## Fixtures and comparison rules

`app/fixtures/sr_inspections_v1.json` contains 37 regression transcripts, including
the exact previous live transcript, a Log #25 regression, Cyrillic, spoken counts,
all honey band categories, negation, unknowns, uncertain ASR, unsupported brood
coverage, explicit scales/trends, plans, performed actions, contradictions and
untrusted transcript instructions. The original 20 transcript strings are unchanged;
the medium-band expectation is now null with required notes, and angry behavior
requires a source excerpt. Nine new cases cover an explicitly good band, aggressive
versus nervous behavior, eggs without direct queen sighting, treatment without a
Varroa level, weak versus absent descriptive pollen intake, brood coverage without
a frame count, completed foundations without a count and unverified health signs.
The integrity pass adds eight cases for unrelated negatives, mixed positive and
unchecked observations, Log #2, accusative/ordinal identity, shared-noun multiple
IDs and unrelated numbers. Existing transcript strings are preserved;
`absent_flags` now spells out the previously implicit null brood/queen expectations.
The fixture format version is independent of
the dictionary and prompt versions.

Each case has `id`, `transcript`, an `expected` Pydantic payload and optional
`note_contains` source excerpts. Omitted structured fields are expected to be null.
The comparator reports missing non-null facts, wrong non-null values, unsupported
non-null extractions and missing required note excerpts. Explicit zero is a fact.
All structured hive fields are checked too. Free-form `inspection.note` and
`hive.notes` are not compared for exact equality; required excerpts are checked in
`inspection.note`, ignoring case. `actions_taken` is compared literally when an
expected value is supplied, so equivalent paraphrases may need manual review.

`fact_recall` is the fraction of expected non-null facts that match, including hive
identity. Unmentioned nulls do not inflate it. Unsupported extractions and missing
notes are reported separately and prevent a case from passing. Extraction failures
remain in the denominator and count their expected facts as missing. Use all these
counts and case passes together; recall alone does not establish factual quality.

## Running tests and evaluation

From the repository root, use an environment with the lightweight test dependencies:

```bash
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install -r assistant-api/requirements-test.txt
PYTHONPATH=assistant-api python3 -m pytest -q assistant-api/tests
PYTHONPATH=assistant-api python3 -m compileall -q assistant-api/app assistant-api/tests
```

The CLI never imports the API application, pipeline, database or Whisper. It never
writes inspections or transcripts. Its three modes are explicit:

```bash
# Validate the dictionary, fixtures and prompt construction; no model calls or accuracy claim.
PYTHONPATH=assistant-api python3 -m app.evaluate

# Replay previously saved raw responses through the application's parser and comparator.
PYTHONPATH=assistant-api python3 -m app.evaluate --responses /tmp/responses.json

# Live comparison using the same configured Ollama model for both prompt versions.
PYTHONPATH=assistant-api python3 -m app.evaluate --live --compare > /tmp/ya-01-1-results.json
```

Replay input is a JSON object keyed by case id. Each value is a raw model response
string or a payload object; all selected case ids must be present. This exercises
the application parser/validator and evaluator, without running a model. It does
not prove live accuracy. Tokens, model name and inference duration are null in
offline reports; the selected prompt version is only configuration metadata there.

For live mode, export the same `OLLAMA_BASE_URL`, `OLLAMA_MODEL` and optional
`OLLAMA_FORMAT` as the application. The CLI does not automatically source `.env`.
If using the repository's trusted configuration locally:

```bash
set -a
. ./.env
set +a
PYTHONPATH=assistant-api python3 -m app.evaluate --live --compare \
  --case previous_live_asr --case explicit_negation
```

The Docker hostname `ollama` may only resolve inside the Compose network. When
running on the host, use the already published port if available, without changing
the configured model or starting/restarting any service:

```bash
OLLAMA_BASE_URL=http://127.0.0.1:11434 PYTHONPATH=assistant-api \
  python3 -m app.evaluate --live --compare
```

For the manual comparison on **yard-mill-01**, first make the finalized source
available there and install the lightweight dependencies in a host Python
environment. From that repository's root, using its trusted `.env`:

```bash
set -a
. ./.env
set +a
OLLAMA_BASE_URL=http://127.0.0.1:11434 PYTHONPATH=assistant-api \
  python3 -m app.evaluate --live --prompt-version hive_semantics_v2 \
  > /tmp/ya-01-1-v2.json
OLLAMA_BASE_URL=http://127.0.0.1:11434 PYTHONPATH=assistant-api \
  python3 -m app.evaluate --live --prompt-version hive_semantics_v2_1 \
  > /tmp/ya-01-1-v2_1.json
# Or evaluate both in one report:
OLLAMA_BASE_URL=http://127.0.0.1:11434 PYTHONPATH=assistant-api \
  python3 -m app.evaluate --live --compare > /tmp/ya-01-1-comparison.json
```

These manual commands preserve the configured model and do not use the API or
SQLite. No server connection, deployment or container restart was performed during
this finalization.

Single text, file and stdin inputs are supported. `--expected` accepts a JSON file
containing the expected Pydantic payload; single-text replay uses case id `text`.
Without expected values, live text mode reports the extraction and metadata only.

```bash
PYTHONPATH=assistant-api python3 -m app.evaluate --live \
  --text 'Košnica broj 1. Tri rama sa leglom. Nema larvi. Maticu nisam tražio.'
PYTHONPATH=assistant-api python3 -m app.evaluate --live \
  --text-file /tmp/inspection.txt --expected /tmp/expected.json
printf '%s' 'Košnica 1. Matica viđena.' | \
  PYTHONPATH=assistant-api python3 -m app.evaluate --text-file - --live
```

Use repeated `--case ID` flags to select fixtures, or `--fixtures PATH` for another
fixture file. `--prompt-version hive_semantics_v2` selects the baseline alone.
`--compare` requires `--live`. Reports are JSON, with per-case results and per-prompt
summaries. They include returned model name, prompt version, `prompt_eval_count`
and `eval_count`, request/validation/total milliseconds and Ollama inference
`eval_duration` in nanoseconds when available. Absent server telemetry remains null.
Exit codes: 0 for validation/success, 1 for extraction failures or comparison
differences, 2 for invalid input/configuration files or CLI arguments.

To inspect phrase selection without HTTP or SQLite:

```bash
PYTHONPATH=assistant-api python3 - <<'PY'
from app.terminology import load_terminology
from app.services import build_system_prompt
text = 'Nije los venac. Pčele su izrazito agresivne. Maticu nisam tražio.'
print(load_terminology().hints(text))
print('System prompt characters:', len(build_system_prompt(text)))
PY
```

Expected policies include `honey_bands: uncertain`, `queen_seen: unknown`, and
`behavior: note_required` alongside the closest `nervozne` mapping. This confirms
selection only, not model-level Serbian understanding.

## Validation status and limits

The deterministic suite covers existing YA-01 behavior plus terminology validation,
accent/Cyrillic synonym matching, polarity/uncertainty hints, prompt selection,
fixture contracts, strict response replay, comparator errors, failure accounting,
telemetry and CLI isolation from audio and persistence. Mocked fixture responses
check wiring and expected contracts; they do not test Serbian understanding.
The earlier Phase A finalization expanded its 190-test baseline to 298 tests.
This integrity pass started from those **298 passing tests**; the complete suite
now passes **382 tests** (84 additional regressions), including the existing YA-01
tests. Python compilation, both JSON documents and Git whitespace checks passed.
All **37 fixtures** passed offline validation and replay of constructed expected
responses with both prompt versions. Replay verifies parser/comparator compatibility,
not model accuracy. The CLI regressions also reject the actual `absent_flags`
unsupported zeros and unsupported positive/negative interpretations of Log #2.
The suite emitted 20
existing Starlette/AnyIO deprecation warnings. In the restricted execution
environment, TestClient's event loop hung inside the sandbox; the full suite
passed when run outside it. Extraction-only tests also passed inside the sandbox.

The earlier Phase A validation reported that on 2026-10-29 the configured
`http://ollama:11434` could not be reached for either
v2 or v2.1 on the previous live transcript using configured `llama3.1:8b`.
The published host endpoint `127.0.0.1:11434` also refused connections. No live
accuracy comparison was possible then; connection failures are not accuracy
results. This integrity pass made no live Ollama calls, did not recheck server
availability and did not connect to `yard-mill-01`.

The corrected static v2.1 prompt is **5,224 characters**, up from 4,305 (+919).
Across the original 20 fixture transcripts, full prompts including selected hints
average **5,445.75 characters**, up from 4,526.75 (+919); the new range is
5,310–5,678. Across all 37 fixtures the range is 5,224–5,678. Only matched phrases
are injected; the full dictionary is never appended. These are character counts,
not measured token counts, inference timings or accuracy improvements.

Remaining limits: the dictionary is curated and not an exhaustive Serbian
morphological parser. Clause negation, uncertainty and factual selection are LLM
instructions, not deterministic semantic guarantees. ASR corruption cannot always
be resolved, strict schema validation cannot detect all plausible hallucinations,
and note wording/actions may need human review. A live model run is still needed
to measure coverage and prompt token/runtime cost. Synthetic fixtures do not
replace review on representative recordings. No health analysis or UI redesign
is included in this phase.
