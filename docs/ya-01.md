# YA-01: factual extraction and data integrity

This is the current v2 contract and operating guide. All pre-v2 records are
synthetic development data. No deployed database was accessed or changed during
implementation. No migration runs on startup. The API refuses missing/legacy
schemas and explains the explicit initialization/reset procedure.

## Pipeline and persistence

1. Whisper transcribes the upload. The exact concatenation of segment text is
   retained, including whitespace. No LLM rewrite replaces it. Uploads are limited
   to 32 MiB. If transcription fails, no record is created; keep the source audio.
2. Commit a `hive_logs` row containing the original uploaded audio, original
   Whisper transcript, server UTC timestamp and Whisper timing/model metadata.
3. Claim a persisted `extraction_attempts` row. A partial unique index prevents
   concurrent attempts on the same source. No SQLite transaction spans an LLM call.
4. Call the configured Ollama model once, with the versioned v2 system prompt,
   temperature 0 and a JSON schema from Pydantic. The model selection is unchanged.
   This follows [Ollama's structured output API](https://ollama.com/blog/structured-outputs).
   For older servers, explicitly set `OLLAMA_FORMAT=json`; schema is the default.
   There is no silent format downgrade or automatic retry.
5. Parse the entire response as JSON, validate strict types/bounds/enums and forbid
   unexpected fields. Canonicalize Serbian hive numbers in Python. A clearly
   conflicting identifier fails validation; multiple identifiers become `UNKNOWN`.
   A unique transcript identifier supplies a missing model ID. Without a recognized
   transcript identifier, even a model-supplied ID becomes `UNKNOWN`. Identity
   decisions and conflicts are retained in the existing attempt metadata; conflicts
   fail with `hive_id_conflict` before any hive/inspection is written.
6. Commit the model response, validated extraction and metadata to the attempt
   **before** normalized persistence. Invalid output remains available for diagnosis.
7. In one transaction, insert hive/inspection and mark normalization complete.
   Failure rolls back all normalized writes. The source and extracted candidate
   remain committed. Mark failures explicitly in the source and attempt.
8. Every inspection has a unique `raw_log_id` and `extraction_attempt_id` plus
   foreign keys. Reprocessing a completed source returns its existing inspection;
   it never overwrites a historical inspection or creates a duplicate.

The database has `hive_logs`, `extraction_attempts`, `hives`, `inspections` and a
latest-inspection view. There is no active metrics table or analytical contract.
`PRAGMA user_version=2` identifies the schema. `DB_PATH` takes precedence over the
accepted `DATABASE_PATH` alias, then `/data/logbook.sqlite` is the default.

## States and API

Extraction and normalization independently use `pending`, `completed`, `failed`.
Normalization `pending` means it has not run, including after extraction failure.
An attempt's overall `status` is completed only after normalized commit. Sources
can remain pending after an interrupted worker. There is no background queue.

- `POST /api/voice` and `POST /voice`: 200 for a completed inspection; 201 when the
  source is saved but processing fails. Both include `id`, `preview`, processing
  statuses, `inspection_id`, `confirmation_status` and an error object or null.
- Bad/empty audio: 400/422; uploads over 32 MiB: 413. No source record is promised.
- Raw persistence failure: 503, no saved ID. Keep the recording and retry later.
- Failure to start processing or update status after the source commit: 503 **with
  the saved ID**. Do not upload again; inspect/reprocess the saved source.
- `GET /api/logs/{id}`: source preview, persisted inspection and all attempt details.
- `GET /api/logs/{id}/audio`: original binary attachment; synthetic seeds have none.
- `POST /api/logs/{id}/reprocess`: 200 with explicit processing result; 409 if an
  attempt is already running. Retries use the saved transcript, not a new recording.
- Unknown source/inspection: 404.
- `GET /logs/{id}`: review the original transcript, persisted facts and attempts.
- `POST /api/inspections/{id}/confirm`: idempotently confirms review and records UTC
  confirmation time. Persistence starts as `unreviewed`; extraction success never
  implies human confirmation. Field editing and correction history are deferred;
  no endpoint rewrites source text or existing facts.

If the database becomes unwritable even for the failure-status update, the response
has `status_persistence_error` and the original saved ID. The last persisted state
may remain pending. Stop the API, resolve storage problems, recover pending attempts
explicitly, then reprocess. Nothing automatically recovers running attempts:

```bash
cd assistant-api
python3 -m app.db_cli --db /path/to/logbook.sqlite recover-pending --api-stopped
```

`--api-stopped` is an operator assertion, not automatic process detection.

## Factual contract

The root contains required `hive` and `inspection` objects. `hive.hive_id` is a
required nullable key. Other observations are nullable and never default to a
quick inspection, inferred reserves or a strength assessment. Flags are integer
0/1, counts are nonnegative integers, invalid values fail the entire extraction.
Application timestamps and original text are outside the model's contract.
Scores, readiness, risk estimates, recommendations and predictions are rejected.
`actions_taken` records only actions actually stated as performed.

Serbian numbering handles digit identifiers of any positive number, Latin/Cyrillic,
common cardinal words through 100 and ordinal forms 1–10. Ambiguous or unfamiliar
spoken identifiers still need review. LLM semantic accuracy is not guaranteed by
schema validation.

For Log #25, the deterministic fixture validates H1, calm behavior, queen seen,
4 brood frames, open and capped brood and 5 honey frames. “Ima sveže zasijanog”
remains text with `eggs_seen=null`; “Pogača pojedena do pola” remains in note without
inferring low reserves. The mocked test validates this contract; it does **not**
prove a live model will extract it. Review against the source audio/transcript.

## Retention, access and observability

Original audio/text and attempt responses are retained in the same SQLite database
for the lifetime of the logbook. Reprocessing retains earlier attempts. There is
no automatic expiry/purge and no routine transcript/response logging. Review/API
and exports expose these audit details through the existing trusted deployment;
no authentication service was added. Keep access within the existing trusted
network. JSON/SQLite exports and backups include audio and model responses; CSV
contains inspection facts and linkage. Development reset removes the active
records but retains the required backup; deleting backups is a separate operator
retention decision. Future real-data retention needs a deliberate policy.

Structured application logs contain IDs, stages, safe error codes and timings:
Whisper, Ollama request, parsing/validation, raw/normalized SQLite persistence and
total processing. Ollama nanosecond durations, token counts, returned model ID,
format and prompt version are retained per attempt when supplied. No credentials,
connection URLs or entire inputs are logged by the pipeline.

## Exports and compatibility

Existing UI routes, voice aliases, `id`/`preview` and all three export routes remain.
`preview.structured` is the new factual contract and is null on failure; it is
built from committed facts on success. Synthetic legacy database/JSON shapes are
intentionally replaced. External clients expecting `metrics` need updating.

- `/export/json`: schema version, exact source transcripts, audio as base64, factual
  inspections and every attempt/error/model response/metadata. JSON strings in
  `payload_json`, `metadata_json`, `whisper_metadata_json` remain strings.
- `/export/csv`: latest hive snapshot, preserving previous column names/order.
  Removed analytical columns are blank.
- `/export/inspections.csv`: all historical inspections, one row per stable ID,
  source/attempt links, application timestamp, facts and extraction/review statuses.
  Sources with no normalized inspection appear in JSON and the transcripts UI.
- Both CSVs use UTF-8 BOM, CRLF, standard CSV quoting and apostrophe escaping for
  formula-like text. JSON/SQLite preserve original text without CSV escaping.
- `/export/sqlite`: consistent temporary snapshot using SQLite backup API, including
  committed WAL contents; temporary file removed after download.

## Local setup and tests

From repository root, in a Python environment with venv support:

```bash
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install -r assistant-api/requirements-test.txt
PYTHONPATH=assistant-api python3 -m pytest -q assistant-api/tests
python3 -m compileall -q assistant-api/app assistant-api/tests
```

Tests mock Whisper/Ollama; no GPU/model packages, network or running services are
required. They cover failures, validation, lifecycle transactions, duplicate
prevention, review, exports (including WAL snapshots/formula injection), repeated
initialization, legacy refusal and reset/backup on disposable databases.
The initial implementation suite passed 92 tests. Live GPU, audio decoding,
real-model extraction and browser microphone behavior were not exercised.

Create and seed a local development database (no models required):

```bash
cd assistant-api
python3 -m app.db_cli --db ../data/logbook.dev.sqlite init
python3 -m app.db_cli --db ../data/logbook.dev.sqlite seed
python3 -m app.db_cli --db ../data/logbook.dev.sqlite check
```

`init` is repeatable on a compatible database and refuses legacy tables. `seed`
requires an empty database and inserts one deterministic synthetic inspection; it
never calls Whisper/Ollama. It is never invoked during startup. Install normal
`requirements.txt` to run the API, then set `DB_PATH` to the same absolute file.

An explicit development reset, **only after stopping the API**:

```bash
cd assistant-api
python3 -m app.db_cli --db ../data/logbook.dev.sqlite reset \
  --confirm-delete-synthetic-data --api-stopped \
  --backup ../data/logbook.dev.before-reset.sqlite
python3 -m app.db_cli --db ../data/logbook.dev.sqlite seed
```

The backup destination must not exist. Reset can replace a legacy synthetic
schema, checkpoints its WAL, backs it up using SQLite, builds a fresh schema and
atomically replaces the selected file. Never invoke it against real records.
It changes no Docker volumes, storage mounts or services.

## Manual deployment and rollback

These instructions are for the operator; they were **not executed**. Run at the
repository root on the deployment host after code review. Keep the configured
Whisper/Ollama models and all GPU/network/mount settings unchanged.

1. Preserve the current image/config and build only the API:

   ```bash
   docker image tag "$(docker inspect --format '{{.Image}}' assistant-api)" yard-assistant-api:pre-ya01
   cp -p .env .env.before-ya01
   docker compose build assistant-api
   ```

2. Back up the currently configured database with the new image's CLI. Choose a
   new backup filename inside the existing `/data` mount:

   ```bash
   docker compose run --rm --no-deps assistant-api python3 -m app.db_cli backup /data/pre-ya01.sqlite
   ```

3. Initialize a **new** v2 database alongside the old one. This avoids resetting or
   migrating existing synthetic records and makes rollback straightforward:

   ```bash
   docker compose run --rm --no-deps -e DB_PATH=/data/logbook.ya01.sqlite assistant-api python3 -m app.db_cli init
   ```

   For development only, optionally seed that same explicit path:

   ```bash
   docker compose run --rm --no-deps -e DB_PATH=/data/logbook.ya01.sqlite assistant-api python3 -m app.db_cli seed
   ```

4. Stop only the API, edit `.env` to set `DB_PATH=/data/logbook.ya01.sqlite` (the old
   file remains untouched), then start the built API without touching Ollama:

   ```bash
   docker compose stop assistant-api
   # Edit DB_PATH in .env now; do not change model/GPU/network settings.
   docker compose up -d --no-deps assistant-api
   curl --fail http://127.0.0.1:8000/health
   ```

   Verify an upload, partial failure, review/confirmation, reprocessing and all
   exports on synthetic records before introducing real beekeeping observations.
   If the installed Ollama rejects schema format, explicitly set
   `OLLAMA_FORMAT=json` in `.env` and recreate **only** the API. Review its extraction.

Rollback code/config/database together. The old database was never replaced:

```bash
docker compose stop assistant-api
cp -p .env.before-ya01 .env
cat > /tmp/yard-assistant-rollback.yml <<'YAML'
services:
  assistant-api:
    image: yard-assistant-api:pre-ya01
    pull_policy: never
YAML
docker compose -f compose.yml -f /tmp/yard-assistant-rollback.yml up -d --no-deps --no-build assistant-api
curl --fail http://127.0.0.1:8000/health
```

Do not point old code at the v2 database. Keep the v2 file/export if it contains
records worth reviewing; rollback does not copy v2 records into the legacy schema.
If you chose the destructive development reset instead of a new filename, stop
the API and restore the matching pre-reset SQLite backup before running old code.
