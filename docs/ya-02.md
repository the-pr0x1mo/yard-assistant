# YA-02: Review and correction

## Inspection before implementation

Work is on `ya-02-review-and-correction`, already based on local `main` at
`82245cd`. The pre-existing local edit to `hive_semantics_v2.txt` is preserved;
YA-01.1 extraction changes are outside this work.

The existing v2 schema supports the workflow without DDL. `whisper_metadata_json`
can hold an idempotency identifier; existing unique source/attempt links remain.
`BEGIN IMMEDIATE` serializes confirmation lookup and insertion across processes.
No table, index, view, foreign key, database path, or `user_version` is changed.
The existing `v_hive_latest` includes unreviewed YA-01 rows, so application queries
select the latest **confirmed** row directly without changing the view.

## Behavior and persistence

Whisper processes temporary audio, preserving exact segment text. Temporary audio
is deleted on transcription success or failure. Audio bytes and content types are
NULL in every newly created log. Neither audio nor an unconfirmed draft is stored
in another database, files, browser storage, cookies, or sessions.

Ollama is called once using the existing factual contract. The server returns a
review with editable structured fields and an expandable, read-only transcript.
Extraction failure returns a usable review with NULL facts; manual confirmation
records the AI attempt as failed and human persistence as completed.

The review token contains a signed copy of the original transcript, extraction
result and metadata, a random review ID, and creation time. It is signed, not
encrypted; treat it like the transcript. The browser keeps it only in the active
page's memory. It is sent in the confirmation body, never a URL. Responses use
`Cache-Control: no-store`. Reload, close, discard, navigation and browser back/forward
cache departure lose unsaved cards. An unload warning protects unsaved data,
subject to browser restrictions on unload prompts.

Confirmation validates the selected hive, inspection date and complete factual
fields, then in one SQLite transaction:

1. Check whether this review ID already has an inspection.
2. Select an existing hive or create a unique new hive; save its display name.
3. Insert the original transcript and Whisper metadata without audio.
4. Insert the extraction attempt, keeping its actual success/failure and error.
5. Insert the user-approved inspection as `confirmed`, including `confirmed_at`.

A failed transaction rolls everything back, including a hive rename. A repeated
confirmation returns the committed inspection without applying later changes in
the retried request. The browser retains the review after request failure. There
is no durable draft store. A successful confirmed correction updates the same
inspection, leaving its ID, hive reference, source/attempt links and original
confirmation timestamp unchanged. PUT replaces all factual fields; omitted facts
become NULL. Corrections never invoke Whisper or Ollama.

Human-selected hive IDs are exact stable keys: 1–64 ASCII letters/digits plus
`_`, `-`, `.` (first character alphanumeric). `UNKNOWN` is rejected. Spoken AI hive
normalization is unchanged. Existing IDs cannot be renamed; only `hives.name`
can change. Names are optional, up to 200 characters. No hive deletion is added.

Inspection dates accept `YYYY-MM-DD` or ISO local date/time through seconds. The
UI explicitly displays UTC, consistent with existing server timestamps. Unknown
flags are NULL; Yes/No are integer 1/0. Blank numeric fields remain NULL; integers
must be nonnegative within SQLite's signed 64-bit range, with existing smaller
bounds/enums retained. Temperatures retain the existing signed real constraint.

## API changes

| Route | YA-02 behavior |
|---|---|
| `POST /api/voice`, `POST /voice` | 200 review on transcription success, including extraction failure. `status=review`, `id=null`, `inspection_id=null`, `review_token`, `inspected_at`, `preview`, explicit extraction/error states. No database writes. |
| `POST /api/reviews/confirm` | New. Accepts token, `hive: {hive_id, name, create}`, `inspected_at`, and `inspection`. Returns stable `inspection_id`, log `id`, and confirmed status. |
| `GET /api/hives` | New. Existing selectable IDs/names, excluding `UNKNOWN`. |
| `PATCH /api/hives/{id}` | New. Accepts `{name}` only; never changes the primary key. |
| `GET /api/inspection-fields` | New. Serbian labels/grouping and controls derived from the existing factual schema. |
| `PUT /api/inspections/{id}` | New. Replaces date and factual fields of a confirmed inspection; rejects immutable/linkage/source fields and unknown keys. |
| `POST /api/inspections/{id}/confirm` | Retained for explicit review of YA-01 unreviewed inspections; optional complete correction body. Already confirmed requests are idempotent. |
| `GET /api/logs/{id}`, `GET /logs/{id}` | Retained. Persisted facts, original transcript, inspection editor. API keeps attempt details. |
| `POST /api/logs/{id}/reprocess` | Existing inspection returns persisted data. A legacy source without an inspection gets an ephemeral review; no attempt or inspection is written until confirmation. Never runs automatically. |
| `GET /api/logs/{id}/audio` | Only legacy audio remains downloadable until operator cleanup; new logs return 404. |

Malformed data returns 422; missing records 404; hive conflicts/invalid tokens
409; SQLite write failures 503 with retry instructions. Empty/invalid audio
400/422 and the 32 MiB upload limit (413) remain. A 200 upload now means a review
was prepared, not that an inspection exists. Clients must explicitly confirm.

JSON and inspection CSV contain confirmed inspections with **current corrected
facts**. JSON includes their linked transcripts and original attempts, omitting
all audio fields; it no longer exports every failed/unreviewed legacy source.
Latest-hive CSV/dashboard use the latest confirmed row; existing CSV columns and
spreadsheet formula escaping remain. Transcript history retains older YA-01
records for review; these do not count as official inspections.

`/export/sqlite` remains a complete consistent database snapshot, including legacy
states, but removes audio from the **temporary copy** and compacts it before
sending. It does not alter the source database. This download is not a complete
retention backup of old audio. `db_cli backup` remains the full operator backup,
including legacy audio and committed WAL data.

## Audio cleanup: operator action only

Never runs on startup or deployment. Not run on production during development.
Stop the API and any other writers first; `--api-stopped` is an operator assertion.
Use a new backup filename on the existing storage mount:

```bash
docker compose stop assistant-api
docker compose run --rm --no-deps assistant-api python3 -m app.db_cli cleanup-audio \
  --api-stopped --confirm-remove-audio --backup /data/before-audio-cleanup.sqlite
```

The command uses SQLite's backup API (including committed WAL pages), verifies
backup integrity, foreign keys, schema/version and every table's contents against
the current database while holding a write lock, then transactionally sets only
`audio_bytes`/`audio_content_type` to NULL. Missing flags, an existing backup path,
failed verification or intervening writes abort without removing audio. Transcripts,
inspections and links remain. Review the command result before restarting the API.

Removing BLOB values may **not reduce the physical database file size**. Old
content can remain in free pages, WAL files and backups. This is logical removal,
not forensic erasure. Optional offline checkpoint/VACUUM and backup retention are
separate operator decisions after verification and with adequate free disk space.
Do not copy a live WAL database's main file as a backup, or delete WAL sidecars.
The verified backup intentionally retains the original audio.

## Safe deployment and rollback

No deployment, production changes, audio cleanup or merge is performed by this
implementation. Preserve the existing DB_PATH/DATABASE_PATH, mounts, services,
models, GPU, network and TLS settings. Use the same production v2 database.
**Do not run init, reset, seed, or migration commands for this upgrade.**

1. Review changes, run tests and manual browser checks on disposable data. Preserve
   the running image under `yard-assistant-api:pre-ya02` and copy the current config
   to `.env.before-ya02` before building. Build only `assistant-api`.
2. Finish or discard active reviews; stop the API and all other writers. Using the
   new image's CLI, run `check`, then `backup /data/pre-ya02.sqlite` with a fresh
   filename. Verify backup integrity and retain it with the old image/config.
3. Start only the new API: `docker compose up -d --no-deps assistant-api`. Check
   `/health` reports schema 2, then confirm the review workflow. No schema or path
   change is needed. Review old unreviewed rows explicitly; nothing auto-confirms.
4. Keep a single API worker unless `REVIEW_SIGNING_KEY` is explicitly configured
   with a strong secret shared by all workers. Without it a per-process random key
   is used; restarting invalidates open reviews. The current Docker command has
   one worker. Do not log tokens or put them in proxy access URLs.

Rollback normally requires stopping the API, preserving a **fresh full backup**
of all YA-02 writes, restoring `.env.before-ya02`, and running the retained
`yard-assistant-api:pre-ya02` image with an explicit Compose image override and
`--no-build --no-deps`. The v2 schema is compatible, but old code resumes YA-01's
automatic persistence/audio retention and may fail to render custom human IDs
outside the old spoken-number normalizer. Test this before using code-only rollback.

For a full rollback, archive post-upgrade data first and restore the verified
`pre-ya02.sqlite` snapshot to the **same configured database path** using SQLite's
backup API while every writer is stopped. Open the target through SQLite and
successfully checkpoint its WAL first; never replace only the main file while
leaving a newer WAL attached. Verify integrity/foreign keys/schema 2 before
restarting the retained image. This restores the old data state and excludes
later approved corrections, which remain in the archived YA-02 backup for recovery.

## Remaining limitations

- No draft recovery after navigation; this is intentional. Open-card recovery
  after a process restart requires a stable configured signing key. Tokens have
  no explicit expiry; configured-key reviews can be submitted by a client retaining
  them, although the shipped UI discards them on departure.
- Old unreviewed inspections with `UNKNOWN` IDs cannot be confirmed through the
  compatibility endpoint, which does not rewrite historical hive references.
  They remain visible in transcript history. New reviews require an identified hive.
- Concurrent corrections use last-write-wins; no audit/revision tables or conflict
  history are introduced. Renaming a hive affects its displayed name in all history.
- Date/time controls are UTC; no timezone conversion is introduced. Browser unload
  warnings may be suppressed by browser policy, particularly on mobile.
- Idempotency scans existing JSON metadata under the SQLite write lock; no new
  index is introduced. Review count/scale remains appropriate to a small logbook.
- The browser rejects integer counts beyond JavaScript’s exact integer range; the
  API accepts validated SQLite 64-bit integers.
- Audio-cleanup verification reads complete table contents into memory; run it as
  an offline operator maintenance action with sufficient resources.
